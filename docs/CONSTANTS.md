# 常量管理规范

## 目标

常量用于沉淀跨页面、跨组件或跨业务模块共享的稳定数据。它解决的是“同一份业务事实只维护一次”的问题，不是把组件内部临时状态也提前全局化。

## 目录规则

- 应用内常量统一放在 `src/const/`，按业务模块拆分文件，例如 `regions.ts`、`routes.ts`、`certificate.ts`。
- `src/const/index.ts` 作为统一出口，页面、组件、store、domain 代码优先从该出口导入稳定常量。
- 单个模块常量过大时，可以继续目录化，例如 `src/const/regions/index.ts` 与 `src/const/regions/miraland.ts`。
- 只被单个组件使用的静态数组、按钮配置、局部枚举，默认留在组件或页面私有组件内，不为了“有 const 文件夹”而抽离。

## 数据形态

- 常量应使用清晰的业务字段，不只存展示文案。需要国际化的内容使用多语言对象或 i18n key。
- 需要持久化、路由跳转、编号生成或远程接口对齐的数据，必须提供稳定 `id`、`code`、`number` 等机器可读字段。
- `id` 用于历史数据关联时不能随便修改；展示名、排序和文案变更不应破坏已保存数据。
- `code` 用于对外展示、编号前缀或接口识别时必须唯一且含义稳定。
- `number` 用于排序、正式编号或后台映射时建议使用字符串，避免前导零丢失。

## 来源标注

- 来源于官网、开放 API、设计稿、策划表或第三方资料的常量，必须在常量文件附近标注来源。
- 来源标注至少包含页面 URL 或接口地址；接口来源还应写明请求方式、关键请求体字段、使用的数据字段和最后复核日期。
- 不能确认官方来源的翻译、配置或映射必须标明为临时值，避免后续维护者误判为官方数据。
- 如果常量由脚本同步生成，应同时保留脚本路径、输入来源和生成时间。

## 导出与校验

- 常量文件优先导出不可变数组或对象，并用 `satisfies` 约束业务类型。
- 重要常量应有最小测试，校验数量、唯一性、必填字段和关键默认值。
- 不在页面里复制常量子集；需要筛选时在消费处计算，或在常量模块提供语义化派生常量。
